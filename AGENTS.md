# AGENTS.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Advanced Note Composer is an Obsidian plugin that enhances the built-in Note Composer core plugin, adding richer merge, split, extract, and swap operations for notes (with frontmatter merge strategies, footnote/backlink fixing, heading-aware merging, and templating). It is built on `obsidian-dev-utils`.

## Architecture

- **Root config files** are thin re-exports — actual logic lives in `scripts/` (`eslint.config.mts` → `scripts/eslint-config.ts`, etc.).
- **`src/`** — plugin source:
  - `main.ts` — Obsidian entry point (default export of `Plugin`); imports the global SCSS.
  - `plugin.ts` — `Plugin` class (extends `obsidian-dev-utils` `PluginBase`); `onloadImpl` wires up settings, settings tab, all command handlers, the Prism component, and release notes.
  - `plugin-settings.ts` — `PluginSettings` class plus the `Action`, `FrontmatterMergeStrategy`, `FrontmatterTitleMode`, and `TextAfterExtractionMode` enums; wraps `PathSettings` for include/exclude path filtering. **The two entry forms match differently** (ODU `path-settings.ts` `makeRegExp`): a plain path string compiles to `^<escaped>(/|$)`, so it covers the path **and its whole subtree**, while a `/regular expression/` is used verbatim against the raw path — which is the only way to express "the folder itself, not its contents" (`/^Inbox$/`). Issue #159 was that confusion, so both setting descriptions, the README `Include/exclude paths` section, and `demo-vault/21 …` spell it out, and `plugin-settings.test.ts` pins both forms. (Issue #159's *other* half — the reporter's own regex never persisting — is the unrelated ODU `new RegExp` throw tracked as issue #155.)
  - `plugin-settings-component.ts` — `PluginSettingsComponent` (settings load/save, value validators, legacy-settings converters).
  - `plugin-settings-tab.ts` — `PluginSettingsTab` settings UI (built with `SettingEx`/`SettingGroupEx`).
  - `prism-component.ts` — registers a Prism language for highlighting `{{token:format}}` template tokens.
  - `release-notes-component.ts` — shows version release notes once on layout ready.
  - `swapper.ts` — `swap` logic for exchanging two files or two folders (with optional full folder-structure swap).
  - `headings.ts` — helpers to extract a heading from editor selection/line.
  - `heading-split-recursion.ts` — the two pure helpers behind the recursive split (issue #79 variant c / issue #156). `findNextHeadingToSplit(headings, minLevel)` returns the first heading at the *shallowest* level ≥ `minLevel`, so a note whose levels are skipped (`#` straight to `###`) or out of order still nests faithfully, and each extraction removes that heading's whole subtree so the next call returns the next sibling. `minLevel` is what stops the recursion eating itself: an extracted note still begins with the heading it was named after, so recursing into it with `minLevel` at 1 would extract its entire content into a nested copy of itself forever — callers pass the parent heading's level plus one, which also bounds the depth at `MAX_HEADING_LEVEL` (6). `buildRecursiveSplitPreviewRows(content, headings)` builds the confirmation dialog's list of notes-to-be-created by reusing `heading-sections.ts`'s tree (G52), so a skipped level is previewed at the depth it will actually nest at rather than at its heading level.
  - `horizontal-rules.ts` — `getSelectionBetweenHorizontalRules`, the range finder backing the `Extract between horizontal rules` command. It reads `metadataCache.getFileCache(file).sections`, filters `type === 'thematicBreak'` (which natively covers `---`/`***`/`___` and their spaced/longer variants, and excludes frontmatter delimiters + `---` inside code fences), and returns the `{ start, end }` `EditorPosition` range of the content between the rules nearest the cursor (document edges act as implicit boundaries; the bounding rules are excluded; leading/trailing blank lines are trimmed). Returns `null` when the note has no rules or the resolved section is blank — analogue of `getSelectionUnderHeading`.
  - `markdown-heading-document.ts` — parses markdown into a heading tree and merges documents heading-by-heading.
  - `insert-mode.ts` — `InsertMode` enum (append/prepend).
  - `move-selection-buffer.ts` — `MoveSelectionBuffer`, the transient holder for the "mark selection to move" feature (source note + captured selection + held source-note lock + the permanent notice); shared by the mark/move/cancel command handlers. `isOffsetInsideMarkedSelection` / `isRangeOverlappingMarkedSelection` reject an insert point/range that overlaps the marked text (a point is a zero-length range).
  - `mark-selection-to-move.ts` — `markSelectionToMove()`, the shared helper that locks the source note (blocking mutations), shows the marked-selection notice, and records the mark. The lock is taken with the dev-utils `lockForPath` `shouldReleaseOnAbort: true` + an `onUnlockRequested` callback that clears the buffer (identity-guarded on the mark's unique `abortController` so a stale controller can't cancel a later mark), so `Unlock active note` — which aborts every lock on the note, cancelling all operations that hold one — also releases the lock and tears the mark down (buffer cleared, notice hidden, highlight removed) without any hand-wired `abort` listener. Takes `shouldLockAllNotes`: when off it locks only the source note (`mode: 'file'`); when on it subtree-locks the vault root (`app.vault.getRoot().path`, `mode: 'subtree'`) so every note is read-only until the move completes or is cancelled. Used by the `Mark selection to move` command (passing the `shouldLockAllNotesWhenMarkingSelection` setting) and the split picker's "switch to smart cut".
  - `selection-highlight-component.ts` — `SelectionHighlightComponent`, persistently highlights the captured selection of a pending operation (a smart-cut mark, or a split/extract while its picker is open) in its source note. A CodeMirror 6 `StateField` (`selectionHighlightField`) + `setSelectionHighlightsEffect` (registered once via `plugin.registerEditorExtension`) renders the decorations; `addHighlight(file, ranges)` returns a `Disposable`, and `refresh()` (on add/remove + `active-leaf-change`) dispatches the effect to every markdown editor. The `@codemirror/*` imports are externalized by the dev-utils build, so they use Obsidian's runtime CM instance. Pure range logic (`computeHighlightRangesForFile`, `mergeHighlightRanges`, `buildSelectionHighlightDecorations`) is unit-tested; the workspace/editor glue (`refreshLeaf`) is `v8 ignore`d and confirmed via a desktop integration test.
  - `move-notice-component.ts` — `MoveNoticeComponent`, owns the permanent "Smart cut & paste" notice while a selection is marked. Builds it with up to four `ButtonComponent`s — move to top / bottom / at cursor (each `MoveMarkedSelectionEditorCommandHandlerBase.executeInActiveEditor()`), and Cancel move (`CancelMoveCommandHandler.cancelMove()`). Enabled state is refreshed via each move handler's `canExecuteInActiveEditor()` on `active-leaf-change` + `selectionchange`; the Cancel button is always enabled. The notice is non-dismissable — shown with `shouldHideOnClick: false` and `shouldShowCloseButton: false` (no `X`), so the only way to release the mark is the Cancel move button (or a programmatic `MoveSelectionBuffer.clear()`, which hides the notice); there is no `onHide`/close-confirmation auto-cancel (removed in issue-140, where clicking any button or the `X` was dismissing the notice before the action ran). **Configurable via the `Smart cut & paste` settings** (read from the injected `pluginSettingsComponent` at `showNotice()` time): each of the three move buttons is included only when its `shouldShowMove{ToTop,ToBottom,AtCursor}Button` flag is on (Cancel always shown), and when `shouldShowSmartCutNotice` is off `showNotice()` shows nothing and returns `null` (so `MoveSelectionBuffer` / `MarkedSelection.notice` are `Notice | null`, and `clear()` guards `notice?.hide()`). Defaults are all `true`, preserving the prior always-four-buttons behavior. The notice also carries an always-shown **`Swap with selection`** button (before Cancel move) backed by `SwapMarkedSelectionEditorCommandHandler` (an `ActiveEditorCommandHandlerBase` subclass that is NOT registered as a command, so it has no hotkey / no main-editor key interception — issue #148): it swaps the smart-cut-marked selection with the active editor's current selection via the shared `swap-selection-runner.ts` (`canSwapWithSelection` / `swapWithSelection`, extracted from `SwapWithMarkedSelectionEditorCommandHandler` so both the swap command and the notice button share one code path — G52). The button is enabled only when the mark covers a single selection and `canExecuteInActiveEditor()` passes (source still exists, active editor has a selection, non-overlapping for a same-note swap); on click it clears the mark (releasing the pending source lock, mirroring the move handoff) and runs the swap in a reversible resource-locked transaction that locks both notes. Covered by `move-notice-component.test.ts` + the real-Obsidian `smart-cut-notice-settings.desktop.integration.test.ts` + `swap-marked-selection.desktop.integration.test.ts`.
  - `recent-suggestions.ts` — the ONE place that knows "recently-opened, most-recent-first", shared by every picker (renamed from `recent-folder-suggestions.ts` when it grew the file half). `getRecentFilePaths` wraps `workspace.getRecentFiles` with a single reconciled option set and an explicit `maxCount: 50` (Obsidian's own default is **10**, which silently truncated the recent list); `reorderSuggestionsByRecentFolders` / `reorderSuggestionsByRecentFiles` front-load the resolved folders/files, filtered by the caller's own constraint and de-duplicated, ahead of the fuzzy suggestions (empty query only). Consumers: the merge/move/swap **folder** pickers, the swap **file** picker, and `SuggestModalBase.getRecentFiles()` (which no longer passes its per-type flags — `shouldIncludeFile` applies the same ones). **Issue #158 — why the folder pickers pass `shouldIncludeActiveFile: true`:** Obsidian's `RecentFileTracker` collects the file you just **LEFT**, not the one you just opened (`Workspace`'s active-leaf change calls `recentFileTracker.onFileOpen(newFile, previousFile)` and the tracker collects the SECOND argument), so the note you are on is never at the head of `getRecentFiles()` — visiting A→B→C leaves `[B, A, …]` with C active. A folder picker asked for "the folder I am on" therefore has to prepend the active file itself; de-duplication keeps that prepended copy first even when the active file also sits further down the list. File pickers pass `false`: their source IS the active file and they already exclude it. Confirmed against real Obsidian by `recent-folder-order.desktop.integration.test.ts` on BOTH ends (G99: catalyst 1.13.4 + public 1.12.7), which also asserts the Obsidian-internal premise so a change upstream fails loudly. Note the ordering assertion in `move-folder.desktop.integration.test.ts` is deliberately hard-coded — deriving it from `getRecentFiles()` the way the production code does made it pass under any ordering, which is why #158 shipped.
  - `filename-validation.ts` — regexes for invalid filename characters / trailing dots-or-spaces, plus the shared `fixFileName` that turns typed text into a valid file name (invalid characters and leading/trailing dots-or-spaces replaced per `shouldReplaceInvalidTitleCharacters`/`replacement`; `/` folded into a collapsed single segment when the name is not treated as a path). Extracted out of `SplitItemSelector` once the folder-merge target name (issue #160) needed the same rules; `SplitItemSelector.fixFileName` is now a thin delegate.
  - `folder-headings.ts` — the two pure helpers behind `Should convert folders to headings when merging a folder` (issue #160 item 2). `buildFolderHeadingPlan({ filePaths, rootPath })` returns, per merged note, the heading lines to emit before it and its `depth` below the merged folder; a folder is headed **once** (only for folders not already open at the previous note), the heading level IS the depth (a direct sub-folder gets `#`), capped at `MAX_HEADING_LEVEL`, and a note directly inside the merged folder gets no heading because the merged note already stands for that folder. That level convention is the exact inverse of the recursive split (`heading-split-recursion.ts`, issue #156), where `# A` produces folder `A` — so a note split into a tree and merged back agrees on levels. `demoteHeadings(content, shift)` shifts ATX headings down by `shift` (capped at 6, fence-aware, indentation preserved) and is applied by `ComposerBase` via the `headingLevelShift` param, BEFORE the template is applied so only the note's own outline moves. The plan requires folder-grouped depth-first input order, which is why `MergeFolderIntoFileCommandHandler` walks the folder itself instead of flat-sorting by path (a flat sort interleaves `sub/z.md` with the root's own `zeta.md` and would head a folder twice).
  - `attachments.ts` — the attachment half of issues #160 (item 3) and #161. `isMarkdownAttachment` answers "is this `.md` file really an attachment", matching `PluginSettings.markdownAttachmentSubExtensions` (default `['excalidraw']`) against the file's **base name**, since Obsidian reports `sketch.excalidraw.md` as base name `sketch.excalidraw`, extension `md` (confirmed live on 1.13.4). `collectAttachmentsToRelocate` returns every descendant of a folder that is not one of the notes being merged AND is either referenced by one of them (`metadataCache.resolvedLinks`, which covers embeds) or unreferenced but already at its proper attachment path for a note whose folder contains it (ODU `isAtProperAttachmentPath`). `resolveAttachmentDestination` delegates to ODU `getAttachmentFilePath` — the very function Custom Attachment Location patches, which is why the "custom attachment location integration" issue #161 asked for needs **no** dependency on that plugin (G52/G61). `relocateAttachments` asks `isAtProperAttachmentPath` BEFORE resolving a destination: the destination is de-duplicated against the vault, so an attachment already at its proper path would collide with itself and be renamed `img 1.png` on every run. **`Flatten folder...` needs none of this** — it promotes every direct child, so attachments beside a note and whole attachment sub-folders travel with it (pinned by `flatten-folder.desktop.integration.test.ts`); #161's first ask was based on a premise that does not hold.
  - `attachment-path.test-helpers.ts` — test-only seeds for the three Vault members Obsidian's attachment-path resolution reads (`getConfig`, `getAvailablePath`, `getAvailablePathForAttachments`) plus `TFolder.getParentPrefix`, none of which `obsidian-test-mocks` implements. Excluded from coverage via `scripts/vitest-config.ts`. **This is a gap worth closing in `obsidian-test-mocks`** — until then every suite touching attachment paths needs the seed.
  - `template-tokens.ts` — `resolveTemplateTokens` (the `{{content}}` / `{{fromTitle}}` / `{{parentFolder}}` / `{{date:FORMAT}}` … substitution) plus the exported `TEMPLATE_TOKEN_REG_EXP` that defines what counts as a token. It also exports `resolveFolderTemplateTokens` for templates that name something derived from a **folder** rather than a source/destination note pair — `{{folderName}}` / `{{folderPath}}` / `{{parentFolder}}` — which backs `mergeFolderIntoFileNoteNameTemplate` (issue #160 item 1). Both resolvers share one `replaceAll` driver, the token regex, the common `{{date}}`/`{{time}}` keys, and the "unknown key throws" contract; only their key sets differ, because the note-flavored keys have nothing to resolve against for a folder. Extracted out of `composers/composer-base.ts` once it gained consumers outside the composer engine — `item-selectors/split-item-selector.ts` (the split-into-folder note name) and `plugin-settings-component.ts` (validating that note name) — so both agree with the resolver on token syntax. Unknown keys still throw (`Invalid template key: …`), matching the pre-existing behavior of every template setting.
  - `templater.ts` — type augmentation for the optional Templater plugin API.
  - `command-handlers/` — one class per command (merge file/folder, swap file/folder, extract before/after cursor/current selection/this heading/between horizontal rules, split-by-headings, split-by-headings-recursively), each extending an `obsidian-dev-utils` command-handler base. `extract-between-horizontal-rules` (`ExtractBetweenHorizontalRulesEditorCommandHandler`) computes its range via `horizontal-rules.ts` `getSelectionBetweenHorizontalRules` (disabled when the note has no rules) and then reuses the same `prepareForSplitFile` + `SplitComposer.splitFile()` flow as the other `Extract …` commands. The "smart cut & paste" feature adds `mark-selection-to-move`, `move-marked-selection-here`, and the top/bottom variants, plus `cancel-move` (a `GlobalCommandHandler`). The `unlock-active-note` `GlobalCommandHandler` is **no longer registered by the plugin** — as of `obsidian-dev-utils` 86.0.0 `PluginBase` registers `UnlockActiveNoteCommandHandler` automatically (via its own `commandHandlerComponent`) before `onloadImpl` runs, so the plugin's command batch omits it. The six smart-cut move commands carry a **`Smart cut & paste:`** display-name prefix (their IDs are unprefixed and unchanged, so existing hotkeys survive). `mark-selection-to-move` (via the shared `markSelectionToMove()` helper) holds a `shouldBlockMutations` lock while the mark is pending: by default a `mode: 'file'` lock on the source note only; when the `shouldLockAllNotesWhenMarkingSelection` setting is on, a `mode: 'subtree'` lock on the vault root (`app.vault.getRoot().path`, i.e. `/`, which covers every path via `isChild`) so every note is read-only + mutation-blocked until the move completes or is cancelled. Either way it is one `Disposable` held in `MoveSelectionBuffer` and released via `clear()`. The helper takes the lock with `shouldReleaseOnAbort: true` + an `onUnlockRequested` callback (`() => MoveSelectionBuffer.clear()`, identity-guarded on the mark's `abortController` so a stale controller can't cancel a later mark), so **aborting the lock cancels the entire move** (dev-utils releases the lock on abort, and the callback drops the mark and hides the notice). The `Unlock active note` command is the **library** `UnlockActiveNoteCommandHandler` (constructed with just `{ app, resourceLockComponent }`), which `PluginBase` now registers itself (see above); it is available whenever the active note is covered by a lock — directly (a merge/split operation or the source-only mark lock) or via a `subtree`-locked ancestor (the all-notes mark's root lock) — checked by `resourceLockComponent.isLockedByAncestorForPath`, and on execute calls `resourceLockComponent.requestUnlockForPath(activeFile)`, which resolves the covering owner (the path itself or its `subtree`-locked ancestor), aborts its controller(s) → for a mark that fires `onUnlockRequested` → cancel, and releases the lock. The lock indicator's right-click unlock hits the same abort path, so it also cancels the whole move. Confirmed against real Obsidian by `unlock-active-note.desktop.integration.test.ts` (the source-note write blocked while marked succeeds again after the unlock). The move-into-active-note commands share `MoveMarkedSelectionEditorCommandHandlerBase` (validation, mtime guard, buffer clear, `SplitComposer` handoff); subclasses only supply the insert point via `resolveInsertion()` and, optionally, override `resolveOptions()`. The base also exposes public `canExecuteInActiveEditor()` / `executeInActiveEditor()` (resolve the active `MarkdownView`, delegate to `canExecuteEditor`/`executeEditor`) so the notice buttons can run each command against the active editor. `MoveMarkedSelectionHereEditorCommandHandler` (registered twice via an `isAdvanced` flag for the default and advanced-options commands) keeps the paste-options modal and, via `resolveInsertion()`, returns the target's selection **range** (`getCursor('from')`/`('to')`) so an active target selection is *replaced* (paste-over-selection); with no selection the range collapses to the cursor. `MoveMarkedSelectionToEdgeEditorCommandHandler` (registered once per `InsertMode` → `move-marked-selection-to-top-of-file` / `move-marked-selection-to-bottom-of-file`, no default hotkeys) returns a `null` cursor offset so the composer derives top/bottom from `insertMode`. `CancelMoveCommandHandler` exposes a public `cancelMove()` (used by both its `execute()` and the notice's Cancel button). The move token is created by the shared `createMoveToken()` (`src/move-token.ts`).
  - **Smart cut & paste template.** `PluginSettings.smartCutAndPasteTemplate` (`''` default) is the template applied to *all* smart cut & paste moves (mark → move here / at cursor / to top / to bottom), so a smart-cut paste can be formatted differently from an ordinary split-to-new-file extract. `SplitComposer` carries an `isSmartCutAndPasteMove` flag (set `true` by `MoveMarkedSelectionEditorCommandHandlerBase.executeEditor`, `false`/absent for ordinary `Extract …`/split, including same-note extract from the picker). `SplitComposer.getTemplate` returns `smartCutAndPasteTemplate` first when the flag is on and it is non-empty; when empty it falls through to the existing split → merge resolution (the documented fallback chain). Validated in `plugin-settings-component.ts` (must contain `{{content}}` when non-empty, mirroring `splitTemplate`); shown in the `Smart cut & paste` settings group via `addCodeHighlighter`. It is a global setting only — not per-move overridable in the advanced paste-options modal. Confirmed against real Obsidian by `smart-cut-template.desktop.integration.test.ts` (a move uses the smart-cut template; emptying it falls back to the split template).
  - **Jump to moved content (issue #144).** After a smart cut & paste move, `SplitComposer` selects the just-moved text in the (re)opened target via `selectMovedContentInTarget()`, at its single call site — the post-transaction open block in `splitFile`. That is gated on a `shouldJumpToMovedContent` **constructor param** (default `true`), NOT on a setting read inside the composer: only the command handler knows which move this is. `MoveMarkedSelectionEditorCommandHandlerBase.shouldJumpToMovedContent()` returns `true` unconditionally — a move AT THE CURSOR always jumps, since inserting text at the cursor and then leaving the cursor elsewhere is incoherent, so it is deliberately NOT configurable — and only `MoveMarkedSelectionToEdgeEditorCommandHandler` overrides it, mapping its `insertMode` to `PluginSettings.shouldJumpToMovedContentTo{Top,Bottom}` (**both default `true`**, so the released 5.0.0 behavior is preserved). Two per-direction settings rather than one shared toggle: to-top/to-bottom is "get it out of the way" (stay put) while at-cursor is focused work (follow), and one boolean cannot express the mix. The override uses a ternary, not `switch`/`assertNever` — the constructor already rejects any other `InsertMode`, so a `default` branch would be unreachable and could never be covered. With a jump off nothing else changes: `revealCursor()` still runs inside the transaction, so the cursor stays where the selection was cut from and is scrolled into view, and the target still opens. `selectMovedContentInTarget()` itself is untouched (keep its warning about not following the selection with `setEphemeralState({ line })`, which would collapse it). The two toggles sit in the `Smart cut & paste` settings group under the three show-button toggles. Confirmed against real Obsidian by `move-selection-cursor.desktop.integration.test.ts`, whose two cases pair up: the default-ON case (all three commands select the moved text) is the positive control for the OFF case, which flips both real settings-tab toggles, asserts both edge moves leave the selection empty AND that a move at the cursor still jumps with both toggles off, then restores them.
  - `composers/` — core merge/split engine: `ComposerBase` (frontmatter merge, footnote/backlink/link fixing, templating) with `MergeComposer` and `SplitComposer` subclasses. **Frontmatter `title` on a brand-new target file:** `insertIntoTargetFile` normally drops the merged-in source `title` when the target has no `title` of its own (gated by the `shouldUseSourceTitleWhenTargetHasNoTitle` setting), so merging note A into an existing titleless note B does not let A's title hijack B's identity. For a **brand-new (empty) target file** (`isNewTargetFile`) the choice is instead made by the overridable `shouldKeepSourceTitleForNewTargetFile` field: `MergeComposer` sets it `true` (a merge relocates the whole source note — folder-merge routes every non-colliding note into a fresh target, and merge-file can create one — so the source's `title` must survive, issue #114), while the base default `false` keeps `SplitComposer`'s behavior (a split's new-file title is governed by `frontmatterTitleMode` via `SplitItemSelector`, so it must not inherit the source's). Confirmed against real Obsidian by `merge-folder-title.desktop.integration.test.ts` (a child note with a `title`, merged into a folder with no colliding note, keeps its `title`). The exported `resolveInsertOffset(content, insertMode)` maps an `InsertMode` to a concrete offset (Append = end of note, Prepend = just after frontmatter) and backs both `insertContent`'s append/prepend path and the move flow's top/bottom offset. `ComposerBase` also supports a move mode via an `insertToken` (content replaces the token at the insert point instead of appending/prepending); `SplitComposer.insertTokenIntoTargetFile` derives that offset from `insertMode` when `targetCursorOffset` is `null` (top/bottom), or uses the pinned cursor offset otherwise, and re-maps captured offsets for same-note moves. The token **replaces the `[targetCursorOffset, targetCursorEndOffset]` range** (paste-over-selection when the target has a selection); with no selection the range is empty (`targetCursorEndOffset` defaults to the start), so it is a plain insertion. The same-note offset re-map shifts captured selections by `delta = insertToken.length - (endOffset - startOffset)`. **Same-note split IS a move:** `SplitComposer`'s constructor synthesizes an `insertToken` when `sourceFile === targetFile` (so a same-note extract routes through the same-note-move ordering instead of the broken append/prepend path that would collapse the editor selection and turn the move into a copy), and forces `shouldFixFootnotes`/`shouldIncludeFrontmatter` off for same-note (footnote-fixing would rename+dangle the moved ref; re-including the note's own frontmatter is meaningless). The residual left in the source (link/embed/nothing) is resolved via `textAfterExtractionMode` (a `SplitComposer` param overriding the `Text after extraction` setting; defaults a same-note move to `None` unless the `shouldApplyTextAfterExtractionToSameFile` setting is on) in `replaceSourceSelection`. **Same-note move ordering:** for a same-note move (`isSameNoteMove`) the source selection is removed *before* the target write — the same-file write collapses the editor selection, so a post-write `replaceSelection` would be a no-op (turning the move into a copy); the write reads the post-removal buffer, so the removal survives, and footnote defs need no cleanup (refs + defs stay in the note). Cross-note/split keeps insert-then-remove so `fixFootnotes`/`updateEditorSelections` can extend the selection to also drop orphaned footnote definitions. **Data-loss guard:** `insertTokenIntoTargetFile` aborts (with a notice) when the derived/pinned insert offset falls strictly inside a captured selection (e.g. a same-note "top" move of a selection spanning the frontmatter boundary) — the token would otherwise be deleted with the source; the top/bottom command handlers also gate this in `canExecute` via `MoveSelectionBuffer.isOffsetInsideMarkedSelection`. **Excluded-target guard:** `MergeComposer.mergeFile` calls `ComposerBase.checkTargetFileIgnored`, which normally refuses (with a notice) to merge into a target whose path is excluded/ignored in the settings. The new `shouldMergeIgnoredTarget` param (a `ComposerBaseConstructorParamsBase` boolean, default `false`) skips that guard; the folder-merge handler sets it to the `shouldAlwaysMergeExcludedItems` setting so an excluded item is FULLY merged (content written) rather than left as an empty moved file (issue #150).
  - `item-selectors/` — resolve a chosen suggestion into a concrete target file: `ItemSelectorBase`, `MergeItemSelector`, `SplitItemSelector`. **Split into folder (issue #79):** when the `shouldSplitIntoFolder` setting is on, `SplitItemSelector.createNewMarkdownFileFromLinktext` — after creating the new note at `<dir>/<name>.md` — relocates it into a brand-new folder named after the note (`moveIntoOwnFolder`), so it ends up at `<dir>/<name>/<name>.md`. The folder name is de-duplicated against existing siblings via `getAvailableFolderPath` (numeric-suffix convention, dot-safe unlike `getAvailablePath`), the folder is created with dev-utils `createFolderSafe`, and the empty new note is moved in with `fileManager.renameFile` (no links/backlinks to fix since it is brand-new). Only NEW-target splits/extracts are affected; picking an existing note is untouched, and the whole flow still runs inside the existing resource-locked split transaction. Confirmed against real Obsidian by `split-into-folder.desktop.integration.test.ts`. **Split headings automatically (issue #79, part 2):** the `shouldSplitHeadingsAutomatically` setting (default off) makes heading-driven splits run with no interaction at all. `SplitNoteByHeadings{,Content}EditorCommandHandler` already passed `shouldSkipModal: true` + `heading: headingInfo.heading` (so they never opened the picker and always named each new note after its heading); this setting adds the two missing halves — `ExtractThisHeadingEditorCommandHandler` now passes `heading` plus `shouldSkipModal: <the setting>` (when off, the heading merely seeds the picker input exactly as `extractHeading` did, so behavior is unchanged), and `prepareForSplitFile` skips `confirmSplit` when `shouldSkipModal && shouldSplitHeadingsAutomatically` — deliberately narrower than `shouldAskBeforeSplitting`, which still governs ordinary manually-targeted splits. Combined with `shouldSplitIntoFolder` this yields one heading-named folder per heading, which is what #79 asked for. Confirmed against real Obsidian by `split-headings-automatically.desktop.integration.test.ts` (no picker, no confirmation, note created at `<heading>/<heading>.md`). **Split headings recursively (issue #79 part 3, issue #156):** `SplitNoteByHeadingsRecursivelyEditorCommandHandler` mirrors a note's whole heading hierarchy as a folder tree — `# A` / `## B` / `### C` / `## D` becomes `A/A.md`, `A/B/B.md`, `A/B/C/C.md`, `A/D/D.md`. It is built entirely out of the existing single-level split rather than any path arithmetic: `getSelectionUnderHeading` already extracts a heading *plus its whole subtree*, and `shouldAllowOnlyCurrentFolder` (new note beside its source) composed with `moveIntoOwnFolder` (new note into a folder of its own) makes each pass nest one level deeper, so recursing into each produced note is all that is needed. Three overrides on `prepareForSplitFile` carry that: `shouldForceAllowOnlyCurrentFolder` and `shouldForceSplitIntoFolder` (both forced on, so the folder tree does NOT depend on the `shouldSplitIntoFolder` setting — recursion implies it, since a recursive split without folders cannot express a hierarchy) plus `shouldSkipConfirmation`, because the command confirms the whole restructure ONCE up front (via the shared `ConfirmDialogModal` with `canReselectTarget: false`, gated on `shouldAskBeforeSplitting`, listing every note it will create) instead of once per split. `SplitComposer` is editor-bound (`replaceSourceSelection` writes through the editor), so each produced note is opened in the leaf to recurse into it; the handler reopens the note the command was invoked on in a `finally`, so the leaf does not end up parked on the deepest child. Each split keeps its own reversible resource-locked transaction (`isMultipleSplit: true`, so the composer neither reopens the source nor opens the target), matching the existing multi-split loop. Confirmed against real Obsidian by `split-headings-recursively.desktop.integration.test.ts` on BOTH ends (G99: 1.12.7 public + 1.13.4 catalyst), which drives the real confirmation dialog and asserts the exact tree with `Should split into folder` left OFF throughout. **Split into folder note name (issue #153):** the `splitIntoFolderNoteNameTemplate` setting (empty default = today's behavior) decides what the note inside that folder is called, so every folder split can yield `<dir>/<name>/Overview.md`. `SplitItemSelector.resolveNoteBasenameInOwnFolder` resolves it via the shared `resolveTemplateTokens` (tokens resolve against the note *before* the move, so `{{newTitle}}` is the folder name; `{{content}}` is rejected by the validator as meaningless in a file name), trims a trailing `.md`, sanitizes through `fixFileName` — which gained a second positional `shouldTreatTitleAsPath` parameter, passed `false` so a path-valued token collapses to one segment — and falls back to the folder name on a blank or still-folder-spanning result. No in-folder de-duplication is needed: `getAvailableFolderPath` guarantees a brand-new empty folder. `moveIntoOwnFolder` now RETURNS the overriding base name (or `null`), and `createNewMarkdownFileFromLinktext` feeds it into `isInvalidTitle`, so an overridden name deliberately routes through the existing alias / frontmatter-`title` machinery and the name the note would have had is preserved (`[[Foo]]` keeps resolving). Settings validator in `plugin-settings-component.ts` rejects `{{content}}` plus literal text containing `/` or an invalid filename character. Confirmed against real Obsidian by `split-into-folder-note-name.desktop.integration.test.ts` on BOTH ends (G99: 1.12.7 public + 1.13.3 catalyst).

## Resource locking & transactional rollback

Every merge/split/swap operation (files **and** folders) locks the resources it touches
(`ResourceLockComponent.lockForPath({ shouldBlockMutations: true })`) against edit/delete/rename/move,
detects external changes and aborts, and runs its vault mutations inside a reversible dev-utils
`VaultTransaction` that commits on success and rolls back on cancel/error. The shared runner is
`src/locked-transaction.ts` (`runLockedTransaction`), used by the composers and the swap/merge-folder
handlers; folder-merge threads one spanning transaction into each `MergeComposer`. Requires
`obsidian-dev-utils` ≥ 84.1.0 (`tx.rollback` uses `syncOpenEditorBuffersForPath` so split's rollback
survives an open editor). Unit tests use the real bridge (`App.createConfigured__()` + real
`ResourceLockComponent`/`VaultTransaction`), 100% coverage.

The former integration-only branches are now fully unit-covered against `obsidian-test-mocks` ≥ 3.5.1,
so their `/* v8 ignore */`s are gone: the nested / differently-named folder-swap paths in `swapper.ts`
(3.5.0 made folder rename cascade to descendants and `getAvailablePath` de-duplicate), and the
backlink-rewrite `linkConverter` in `merge-composer.ts` (`fixBacklinks`) — 3.5.0 gave synchronous link
indexing and 3.5.1 fixed the markdown parser's link end offset to the exclusive `start + length`, so
dev-utils' `editLinks` write path now completes against the mock.
