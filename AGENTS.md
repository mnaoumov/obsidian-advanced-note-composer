# AGENTS.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Advanced Note Composer is an Obsidian plugin that enhances the built-in Note Composer core plugin, adding richer merge, split, extract, and swap operations for notes (with frontmatter merge strategies, footnote/backlink fixing, heading-aware merging, and templating). It is built on `obsidian-dev-utils`.

## Architecture

- **Root config files** are thin re-exports — actual logic lives in `scripts/` (`eslint.config.mts` → `scripts/eslint-config.ts`, etc.).
- **`src/`** — plugin source:
  - `main.ts` — Obsidian entry point (default export of `Plugin`); imports the global SCSS.
  - `plugin.ts` — `Plugin` class (extends `obsidian-dev-utils` `PluginBase`); `onloadImpl` wires up settings, settings tab, all command handlers, the tokenized-string language component, and release notes.
  - `plugin-settings.ts` — `PluginSettings` class plus the `Action`, `CommandCategory`, `CommandMenuPlacement`, `EmptyFolderBehaviorAfterMergingFolder`, `FlattenMode`, `FrontmatterMergeStrategy`, `FrontmatterTitleMode`, and `TextAfterExtractionMode` enums; wraps `PathSettings` for include/exclude path filtering. **`CommandMenuPlacement` (issue #252) decides WHICH of Obsidian's two editor context menus a category's commands appear in.** Obsidian raises two and never both for one click: `editor-menu` on the text, and `markdown-viewport-menu` on the empty margin `Readable line length` leaves beside it (and on the line-number gutter) — the editor menu's own handler bails when the click lands outside the editor's `contentDOM`, which is exactly where the margin is. Reaching that second menu needs `obsidian-dev-utils` >= 96.0.0, whose `EditorCommandHandler.shouldAddToViewportMenu` this plugin overrides; before that it was unreachable from a plugin at all. `src/command-menu-placement.ts` owns the two predicates (`checkShouldAddCommandToEditorMenu` / `checkShouldAddCommandToViewportMenu`, both `assertNever`-exhaustive) and is the ONLY place that knows the `'source'` mode literal, so no command handler compares against it. The setting is per `CommandCategory`, reusing the #249 factoring, and `EDITOR_MENU_COMMAND_CATEGORIES` lists the **six** categories it applies to: `Merge` and `Move/flatten` have no `EditorCommandHandler` behind any of their commands, so a placement row on either would control nothing — do not "complete" that list to all eight. Placement COMPOSES with each command's own menu gate rather than replacing it (the selection gate of issue #188 still applies on both menus), and reading mode is deliberately never offered these commands even though Obsidian fires the same event there. **`FlattenMode` (issues #170/#171) collapses the two axes a flatten could have — WHAT moves and HOW DEEP it looks — into ONE enum** (`AllChildren` / `ChildFoldersOnly` / `AllFoldersRecursively`) rather than a scope enum plus a `shouldFlattenRecursively` toggle: the only combination anyone asked for is folders-at-any-depth, and the fourth cell of that cross product (dissolving every descendant FILE into the parent too) is a different operation nobody requested. **It is NOT a setting** — issue #177 turned it into the COMMAND IDENTITY: `plugin.ts` registers one `FlattenFolderCommandHandler` per member (`FLATTEN_MODES`), so the variant is chosen at INVOCATION time from the folder menu, and the settings tab has no flatten-mode row. `AllChildren` reproduces the pre-#170 behavior exactly and keeps the ORIGINAL `flatten-folder` command id, because a hotkey is bound to an id and hotkeys cannot be migrated by a settings converter; the two other ids start unbound. A leftover `flattenMode` key in an existing `data.json` is simply ignored, which is why neither #170 nor #177 needed a `registerLegacySettingsConverter`. `flatten-folder-command-handler.ts` translates the mode through the `FLATTEN_COMMAND_DEFINITIONS` and `FLATTEN_CONFIRM_SUMMARIES` `Record`s (keyed by the enum, so a new member is a compile error rather than a command left unregistered or a dialog left without wording) and hands it to `flatten-items.ts`. **`EmptyFolderBehaviorAfterMergingFolder` is a deliberate plugin-local WRAPPER around ODU's `EmptyFolderBehavior`, not that enum re-exported — do not "simplify" it back.** Issue #167 asked for a fourth option (keep the merged folder, delete the folders under it), and that is a change to WHICH paths are handed to `cleanupEmptyFolders`, not a new per-path behavior, so it is not expressible as an ODU value (G52/G61: nothing to extract upstream). Its three original members reuse ODU's exact string values (`'Delete'`/`'DeleteWithEmptyParents'`/`'Keep'`), which is what makes the retype need **no** `registerLegacySettingsConverter` — every already-persisted `data.json` value is still a valid member. `merge-folder-into-file-command-handler.ts` translates it through the `ODU_EMPTY_FOLDER_BEHAVIORS` `Record` (a `Record` keyed by the enum, so a new member is a compile error rather than an unreachable `switch` default the 100 %-coverage gate must reach) and, for `DeleteSubFoldersOnly` only, filters `folder.path` out of `folderPathsToCleanUp`. That member maps to plain `Delete` and never `DeleteWithEmptyParents`: with the merged folder kept, no ancestor of it can end up empty, so the parent half would be meaningless. **The two entry forms match differently** (ODU `path-settings.ts` `makeRegExp`): a plain path string compiles to `^<escaped>(/|$)`, so it covers the path **and its whole subtree**, while a `/regular expression/` is used verbatim against the raw path — which is the only way to express "the folder itself, not its contents" (`/^Inbox$/`). Issue #159 was that confusion, so both setting descriptions, and `demo-vault/21 …` spell it out, and `plugin-settings.test.ts` pins both forms. **Issue #155 (issue #159's other half — the reporter's own regex never persisting) is fixed**: a partially typed `/regular expression/` used to throw from ODU's `makeRegExp` on EVERY keystroke (`addMultipleText` → `bind` → `setProperty` assigns into `inputValues` *before* validating), popping an unhandled-error notice and aborting the debounced save. Since `obsidian-dev-utils` 88.4.0 `makeRegExp` returns `null` instead of throwing and the `PathSetting.array` setter absorbs it, so **one invalid entry makes the WHOLE list fall back to its default pattern** (`NEVER_MATCH` for Exclude, `ALWAYS_MATCH` for Include — both make `isPathIgnored()` return `false`, so a transient invalid value never hides anything). That fallback is silent by construction, which is why `plugin-settings-component.ts` registers ODU's exported `pathsValidator` on `includePaths`/`excludePaths` (imported, NOT hand-rolled — it was promoted out of Custom Attachment Location for exactly this second consumer) and `appendPathFormsDesc` states the all-or-nothing rule in both descriptions. Confirmed against real Obsidian by `exclude-paths-typing.desktop.integration.test.ts`, which types the reported value character by character and asserts no notice, that the completed value still reaches `data.json` (the save path was the second failure surface), and that an incomplete entry surfaces `Invalid regular expression: …`.
  - **`PluginSettings` holds TWO independent `PathSettings` instances (issue #198), and that split is load-bearing.** `_pathSettings` (`includePaths`/`excludePaths`, surfaced by `isPathIgnored`) is the CONTENT filter: what is off-limits as a picker entry, a merge/split target or source, and what a folder merge / flatten refuses to MOVE. `_commandPathSettings` (`commandIncludePaths`/`commandExcludePaths`, surfaced by `shouldBlockCommandOnPath`) is the COMMAND-VISIBILITY filter: whether the commands are offered at all. They were one list plus a `shouldBlockCommandsOnExcludedPaths` toggle until #198 — the client wanted commands hidden in a subtree that is still a valid merge destination, which one list could not express. **The toggle is REMOVED and must not be reintroduced**: two empty lists already make `isPathIgnored()` `false` (ODU defaults `ALWAYS_MATCH`/`NEVER_MATCH`), which IS the old toggle-off default, so a master switch would only add the incoherent "off, yet paths listed" state. `shouldBlockCommandOnPath` KEEPS its name and signature, which is why `command-block.ts` and the ~20 command-handler test stubs that fake it needed no change. Migration is a `registerLegacySettingsConverter` on `shouldBlockCommandsOnExcludedPaths` that seeds **both** halves from the old lists — the include half matters because the old blocking fired on `isPathIgnored`, which already accounted for `includePaths`, so copying only the exclude half would silently un-block everything outside a configured include list. Note the converter runs on the RAW `data.json` record, not a `PluginSettings` instance, so it reads plain properties rather than the class accessors; ODU then deletes the dead toggle key for free (it is in `LegacySettings` and no longer in `PluginSettings`). All four keys register ODU's `pathsValidator` — the silent all-or-nothing fallback of issue #155 is not specific to the content filter.
  - **Command visibility is narrowable PER COMMAND CATEGORY (issue #249), layered on the pair above rather than replacing it.** `CommandCategory` (eight members: `Merge`, `Split/extract`, `Create`, `Smart cut & paste`, `Swap`, `Move/flatten`, `Rename`, `Reorder`) names the group a command belongs to, and `PluginSettings` holds one `PathSettings` per member behind sixteen accessors (`<category>CommandIncludePaths` / `<category>CommandExcludePaths`), built from `COMMAND_CATEGORIES` — spelled out rather than derived from `Object.values`, which `@total-typescript/ts-reset` types as `unknown[]`, with a unit test comparing it against the enum's own keys. `shouldBlockCommandOnPath(path, commandCategory)` blocks when EITHER `_commandPathSettings` or that category's filter says so, so a category can only NARROW — it never re-opens what the baseline hid, which is the direction the request asked for (block merges here, keep the rest) and is what makes the whole feature need **no** `registerLegacySettingsConverter`: the un-prefixed pair keeps its exact meaning, every category pair starts empty, and two empty lists block nothing. **The category is passed EXPLICITLY at each `isEditorCommandBlocked` / `isFileOrFolderCommandBlocked` call site** (both now take a params object), NOT looked up from the command id — a required argument makes a new command a compile error instead of a silent hole in a mapping table. **Categories, not the ~40 command ids**: the reporter wrote in categories ("merges", "reordering", "renaming folder"), and per-id lists would be eighty settings rows. `cancel-move` and `open-split-modal` are deliberately in no category because neither consults the filter today; letting the second be blocked would be a behavior change beyond the issue. The settings tab renders one group per category from `COMMAND_CATEGORY_SETTING_GROUP_DEFINITIONS` under the group renamed `All commands`, and those headings carry a `commands` suffix (`Merge commands`) because most category names are also settings-PAGE names and a bare `Merge` heading would be a second container by that name — `plugin-settings-tab.test.ts` asserts every category has its group with both rows. Confirmed against real Obsidian by `command-blocking-per-category.desktop.integration.test.ts`, which probes one command per category through `editorCheckCallback`: one category excluded leaves the other three offered on the same path and every category offered elsewhere, three excluded leave the fourth, and the un-prefixed exclude list still hides all four.
  - `plugin-settings-component.ts` — `PluginSettingsComponent` (settings load/save, value validators, legacy-settings converters).
  - `plugin-settings-tab.ts` — `PluginSettingsTab` settings UI, declared through `getSettingDefinitionItems()` (G101). **Its shape is a tree of PAGES, and that is a deliberate answer to an API limitation — do not flatten it back.** Issues #220–#226 asked for collapsible headers collapsed on open (#221), a `Merge` header with `Merge file` / `Merge folder` subheadings (#224), the same for `Include/exclude` (#225) and `Swap` (#226), templates first in every header (#220), the smart cut & paste quality-of-life toggles under the template of the move they belong to (#222), and a `Frontmatter` header (#223). Obsidian 1.13 supports **neither** of the two structural asks: `SettingDefinitionGroup` has no collapsed/collapsible member, and its `items` are `SettingGroupItem = SettingDefinition | SettingDefinitionPage`, so **groups do not nest**. A `SettingDefinitionPage` answers both at once — the tab opens as a short list of navigable entries (nothing expanded, which is what #221's "too much scrolling" actually wanted) and a page holding groups IS the two-level hierarchy the subheader issues needed. **Whether a page has subheadings at all is decided PER PAGE, and two later issues moved two pages in opposite directions — do not "restore consistency" between them.** #240 resplit `Merge` into four (`All merges` + one per command), because a row there is read by exactly one command and a header covering two of them made the other look undocumented; #241 removed both of `Swap`'s (`Swap file` / `Swap folders`), because its shared `Should ask before swapping` row applies to files *and* folders so it belonged under neither, `Swap file` held nothing else, and the three folder rows already name their target type in their own names. `plugin-settings-tab.test.ts` pins both shapes (`collectPageSubheadings` + a per-page row list), so regrouping either one fails there rather than silently. **#243 added a third shape — a page that MIXES a flat row with groups.** `Smart cut & paste` carries `Should lock all notes when marking selection` flat at the top, above its four groups, because that row governs the MARK itself rather than any one notice or move direction, whereas each group is scoped to one of them; a one-row `Marking` heading was rejected as exactly the kind #241 removed. The row lived on `Split/extract` until #243, where nothing read it: both of `split-file-modal.ts`'s uses are its `switch to smart cut` paths, which mark through the same `markSelectionToMove()` the two mark commands use. Obsidian renders the mixed page correctly (flat row first, then the subheadings) — asserted in real Obsidian by `settings-page-navigation.desktop.integration.test.ts`, since the unit test can only see the declared tree. **A third consequence for anything reading the rendered tab: `.setting-group` is NOT the heading.** Obsidian wraps a page's rows in a `.setting-group` even when the page declares no group at all, so counting those elements reports a heading a flat page does not have — it yields the first ROW's name (measured on the rendered `Swap` page while implementing #241). The heading is a `.setting-item-heading` child of the group, which is what `settings-page-navigation.desktop.integration.test.ts`'s `collectSubheadings()` queries, and it runs against BOTH pages so the flat page's empty result cannot pass vacuously on a dead selector. The private `settingPage()` helper next to the inherited `settingEx`/`settingGroupEx` builds them; ODU needs no change, because `PluginSettingsTabBase` never walks `items` (it only stamps `type: 'group'` in `settingGroupEx`), so a page literal passes straight through to Obsidian. **Two consequences bite anything that reads the rendered tab**: a row inside a page is NOT in the DOM until that page is opened, and while a page is open `settingTab.containerEl` is **detached** and still holds the top-level entries rather than what is on screen — which is why every integration test reaches a row through `settings-tab-navigation.ts`'s `findSettingItemInObsidian` (passed into the closure via `evalInObsidian`'s `input`, since a serialized callback cannot reach an import) instead of querying `containerEl`. `Folder note` is the one deliberate exception to #220's template-first rule: its location dropdown decides whether the templates apply at all — it disables the name row outright while the location is `Auto` — so it stays above them, and `plugin-settings-tab.test.ts` records that exception rather than silently tolerating it.
  - `tokenized-string-language-component.ts` — extends `obsidian-dev-utils` `SyntaxHighlightingComponent` and registers, through `registerPrismLanguageAsync`, the Prism language highlighting `{{token:format}}` template tokens. The language is not a code fence — only the settings tab's `CodeHighlighterComponent` fields render it — so only the Prism half of that component is used.
  - `release-notes-component.ts` — shows version release notes once on layout ready.
  - `swapper.ts` — `swap` logic for exchanging two files or two folders (with optional full folder-structure swap).
  - `headings.ts` — helpers to extract a heading from editor selection/line.
  - `heading-split-recursion.ts` — the pure helpers behind the recursive split (issue #79 variant c / issue #156). `findNextHeadingToSplit(headings, minLevel)` returns the first heading at the *shallowest* level ≥ `minLevel`, so a note whose levels are skipped (`#` straight to `###`) or out of order still nests faithfully, and each extraction removes that heading's whole subtree so the next call returns the next sibling. `minLevel` is what stops the recursion eating itself: an extracted note still begins with the heading it was named after, so recursing into it with `minLevel` at 1 would extract its entire content into a nested copy of itself forever — callers pass the parent heading's level plus one, which also bounds the depth at `MAX_HEADING_LEVEL` (6). `buildRecursiveSplitPreviewRows(content, headings)` builds the confirmation dialog's list of notes-to-be-created by reusing `heading-sections.ts`'s tree (G52), so a skipped level is previewed at the depth it will actually nest at rather than at its heading level. `getHeadingSubtree(headings, headingLine)` (issue #228) is the heading starting at that line plus every following heading of a GREATER level — the same bound `getSelectionUnderHeading` applies to the TEXT, applied to the heading cache, so the preview and the extraction cannot disagree about what the subtree is; fed to `buildRecursiveSplitPreviewRows` it yields the scoped command's preview with no second tree walker, and a leaf heading yields just itself (which is what makes the leaf case produce one note rather than nothing).
  - **`Split heading recursively...` (issue #228) is the SAME recursion scoped to one heading, and the two commands share `command-handlers/split-recursively-editor-command-handler-base.ts`.** The base owns the entire flow — ignored-path guard, the single up-front confirmation and its `Change target` loop, the progress/completion notices, the recursion, the deferred split-template pass — because everything BELOW the root pass is already identical: each produced note is recursed into with its own heading's level plus one, bounded by `MAX_HEADING_LEVEL`. The ONE difference is which headings the ROOT pass extracts, and it is expressed as `RecursiveSplitRun.rootHeadingLine`: `null` keeps the whole-note loop over `findNextHeadingToSplit`, a line number extracts exactly that heading and breaks. Subclasses implement only `resolveRun(editor, file, cache)` — the preview rows, the dialog title, the notice verbs, and that line — so `SplitNoteByHeadingsRecursivelyEditorCommandHandler` is now identity + `canExecuteEditor` + four strings. **The entry point is the heading ENCLOSING the cursor** (`getEnclosingHeadingLine`, issue #143), the same rule `Extract this heading...` uses, which is the owner's answer to the three competing entry points raised across #228/#229: right-clicking anywhere inside a heading's section already IS "right-click the header", so the command needs no UI surface of its own and #229's `Smart cut & paste: Mark heading to move` DOES point at the SAME handler — its notice button drives this very command via `ActiveEditorCommandHandlerBase.executeInActiveEditor()`, never a second implementation; the reporter's gutter-widget proposal was declined. The heading is re-resolved in `resolveRun` rather than cached from `canExecuteEditor` (which Obsidian calls on every menu build), so a cursor moved in between cannot split a heading the user has already left. A LEAF heading is deliberately still offered — it produces `X/X.md`, exactly what the whole-note command does at a leaf — rather than hidden the way the flatten variants hide a duplicate of a simpler command, because the result is not the same as `Extract this heading...` (folder forced, no target picker). No new settings: `shouldAskBeforeSplitting`, `shouldSplitRecursivelyIntoDefaultNewNoteFolder` and the forced folder tree all carry over unchanged. Confirmed against real Obsidian by `split-heading-recursively.desktop.integration.test.ts`, which puts the cursor in the BODY of the middle of three same-level headings and asserts both halves: the subtree became a folder tree, and the siblings are still in the source note with their bodies (moving that cursor to a sibling fails the suite, which is how it was validated).
  - `horizontal-rules.ts` — `getSelectionBetweenHorizontalRules`, the range finder backing the `Extract between horizontal rules` command. It reads `metadataCache.getFileCache(file).sections`, filters `type === 'thematicBreak'` (which natively covers `---`/`***`/`___` and their spaced/longer variants, and excludes frontmatter delimiters + `---` inside code fences), and returns the `{ start, end }` `EditorPosition` range of the content between the rules nearest the cursor (document edges act as implicit boundaries; the bounding rules are excluded; leading/trailing blank lines are trimmed). Returns `null` when the note has no rules or the resolved section is blank — analogue of `getSelectionUnderHeading`.
  - `markdown-heading-document.ts` — parses markdown into a heading tree and merges documents heading-by-heading.
  - `insert-mode.ts` — `InsertMode` enum (append/prepend).
  - `move-selection-buffer.ts` — `MoveSelectionBuffer`, the transient holder for the "mark selection to move" feature (source note + captured selection + held source-note lock + the permanent notice); shared by the mark/move/cancel command handlers. `isOffsetInsideMarkedSelection` / `isRangeOverlappingMarkedSelection` reject an insert point/range that overlaps the marked text (a point is a zero-length range). **`MarkedSelection.markedHeading` (issue #229) is what distinguishes a HEADING mark from a plain one** — `{ line, text }`, or `null` for every other mark path — and it is the only thing that makes the notice's heading-only buttons appear and tells them which heading to act on. It is mandatory-but-nullable (**R2 G10s**), so the two `switch to smart cut` call sites in `split-file-modal.ts` pass an explicit `null`: what those switch over is a split's captured SELECTION, even when the split itself was heading-driven.
  - `mark-selection-to-move.ts` — `markSelectionToMove()`, the shared helper that locks the source note (blocking mutations), shows the marked-selection notice, and records the mark. The lock is taken with the dev-utils `lockForPath` `shouldReleaseOnAbort: true` + an `onUnlockRequested` callback that clears the buffer (identity-guarded on the mark's unique `abortController` so a stale controller can't cancel a later mark), so `Unlock active note` — which aborts every lock on the note, cancelling all operations that hold one — also releases the lock and tears the mark down (buffer cleared, notice hidden, highlight removed) without any hand-wired `abort` listener. Takes `shouldLockAllNotes`: when off it locks only the source note (`mode: 'file'`); when on it subtree-locks the vault root (`app.vault.getRoot().path`, `mode: 'subtree'`) so every note is read-only until the move completes or is cancelled. Used by the `Mark selection to move` command (passing the `shouldLockAllNotesWhenMarkingSelection` setting), the `Mark heading to move` command (issue #229 — same helper, a heading section's range as the captured selection plus a `markedHeading`), and the split picker's "switch to smart cut". **It shows the notice BEFORE recording the mark in the buffer**, which is why `MoveNoticeComponent.showNotice` takes the `markedHeading` + `sourceFile` as PARAMS rather than reading them back from `MoveSelectionBuffer`: the first cut read them from the buffer, and the heading-only buttons silently never appeared — a real ordering bug the unit test could not see (it marked first) and the desktop integration test caught immediately (**R2 G10r**).
  - `selection-highlight-component.ts` — `SelectionHighlightComponent`, persistently highlights the captured selection of a pending operation (a smart-cut mark, or a split/extract while its picker is open) in its source note. A CodeMirror 6 `StateField` (`selectionHighlightField`) + `setSelectionHighlightsEffect` (registered once via `plugin.registerEditorExtension`) renders the decorations; `addHighlight(file, ranges)` returns a `Disposable`, and `refresh()` (on add/remove + `active-leaf-change`) dispatches the effect to every markdown editor. The `@codemirror/*` imports are externalized by the dev-utils build, so they use Obsidian's runtime CM instance. Pure range logic (`computeHighlightRangesForFile`, `mergeHighlightRanges`, `buildSelectionHighlightDecorations`) is unit-tested; the workspace/editor glue (`refreshLeaf`) is `v8 ignore`d and confirmed via a desktop integration test.
  - `marked-source-handoff.ts` — `reopenMarkedSourceNote()`, the ONE way a pending smart-cut mark is handed over to an operation that WRITES to its source note: it clears the mark (releasing the `shouldBlockMutations` lock, hiding the notice, dropping the highlight), re-opens the source note in the active leaf, and returns its `MarkdownView` (or `null` when nothing is marked, the note is gone — it notices then — or no markdown view became active). Extracted from `OpenSplitModalCommandHandler.openSplitModal`, which was the only such handoff until the marked-heading notice buttons became the second and third (G52 — one code path, not three). Cancelling the mark is not incidental: the mark's lock blocks exactly the writes those operations perform, so any handoff must give it up first.
  - `move-notice-component.ts` — `MoveNoticeComponent`, owns the permanent "Smart cut & paste" notice while a selection is marked. Builds it with up to four `ButtonComponent`s — move to top / bottom / at cursor (each `MoveMarkedSelectionEditorCommandHandlerBase.executeInActiveEditor()`), and Cancel move (`CancelMoveCommandHandler.cancelMove()`). Enabled state is refreshed via each move handler's `canExecuteInActiveEditor()` on `active-leaf-change` + `selectionchange`; the Cancel button is always enabled. The notice is non-dismissable — shown with `shouldHideOnClick: false` and `shouldShowCloseButton: false` (no `X`), and deliberately **NOT** `isPermanent`: since dev-utils 93 `shouldHideOnClick: false` implies `PluginNoticeMode.Separate` (infinite duration, never replaced by a later notice, which is exactly what this notice wants), and `showNotice` THROWS on `isPermanent` + `Separate` because a permanent notice needs the shared slot a separate one avoids. That throw is what the 93 bump missed — `markSelectionToMove` aborted after taking the source-note lock, so nothing could be marked, moved, or swapped and the lock leaked (12 integration files, all green again once the flag went). Permanence would be wrong regardless: it outlives the plugin, while the mark this notice reports dies with it. So the only way to release the mark is the Cancel move button (or a programmatic `MoveSelectionBuffer.clear()`, which hides the notice); there is no `onHide`/close-confirmation auto-cancel (removed in issue-140, where clicking any button or the `X` was dismissing the notice before the action ran). **Configurable via the `Smart cut & paste` settings** (read from the injected `pluginSettingsComponent` at `showNotice()` time): each of the three move buttons is included only when its `shouldShowMove{ToTop,ToBottom,AtCursor}Button` flag is on (Cancel always shown), and when `shouldShowSmartCutNotice` is off `showNotice()` shows nothing and returns `null` (so `MoveSelectionBuffer` / `MarkedSelection.notice` are `Notice | null`, and `clear()` guards `notice?.hide()`). Defaults are all `true`, preserving the prior always-four-buttons behavior. The notice also carries an always-shown **`Swap with selection`** button (before Cancel move) backed by `SwapMarkedSelectionEditorCommandHandler` (an `ActiveEditorCommandHandlerBase` subclass that is NOT registered as a command, so it has no hotkey / no main-editor key interception — issue #148): it swaps the smart-cut-marked selection with the active editor's current selection via the shared `swap-selection-runner.ts` (`canSwapWithSelection` / `swapWithSelection`, extracted from `SwapWithMarkedSelectionEditorCommandHandler` so both the swap command and the notice button share one code path — G52). The button is enabled only when the mark covers a single selection and `canExecuteInActiveEditor()` passes (source still exists, active editor has a selection, non-overlapping for a same-note swap); on click it clears the mark (releasing the pending source lock, mirroring the move handoff) and runs the swap in a reversible resource-locked transaction that locks both notes. Covered by `move-notice-component.test.ts` + the real-Obsidian `smart-cut-notice-settings.desktop.integration.test.ts` + `swap-marked-selection.desktop.integration.test.ts`. **A HEADING mark (issue #229) adds two more buttons before `Swap with selection`: `Split heading recursively...` and `Reorder headings...`**, each behind its own default-`true` setting (`shouldShowSplitHeadingRecursivelyButton` / `shouldShowReorderHeadingsButton`) and shown ONLY when `showNotice` was handed a `markedHeading` — a plain selection mark has no heading for them to act on. The split button has no enablement predicate (a leaf heading is still a valid recursive split, producing `X/X.md`); the reorder button's predicate is `hasReorderableSiblings` over the **marked** note's headings, not the active editor's, so it is never a button that opens on a note with nothing to reorder. Both drive the EXISTING command through `runOnMarkedHeading`: `reopenMarkedSourceNote` (see `marked-source-handoff.ts`), then `editor.setCursor` on the marked heading line — which is how the cursor-driven commands learn which heading to act on — then `executeInActiveEditor()`. That last call is why `SplitRecursivelyEditorCommandHandlerBase` and `ReorderHeadingsEditorCommandHandler` now extend `ActiveEditorCommandHandlerBase` instead of `EditorCommandHandler` (they drop their own `app` field; it is inherited). For a lock-holding flow (extract/split, merge) closing releases the lock via the `onClose` → `promiseResolve(null)` → `using` chain, so the bar Cancel cancels the whole operation and unlocks the note — the discoverable alternative to the Unlock command that issue #130 asked for (while minimized, the peek-lock suppresses `contextmenu`, hiding the lock-indicator's right-click Unlock menu). ## Resource locking & transactional rollback

Every merge/split/swap operation (files **and** folders) locks the resources it touches
(`ResourceLockComponent.lockForPath({ shouldBlockMutations: true })`) against edit/delete/rename/move,
detects external changes and aborts, and runs its vault mutations inside a reversible dev-utils
`VaultTransaction` that commits on success and rolls back on cancel/error. The shared runner is
`src/locked-transaction.ts` (`runLockedTransaction`), used by the composers and the swap/merge-folder
handlers; folder-merge threads one spanning transaction into each `MergeComposer`. Requires
`obsidian-dev-utils` ≥ 84.1.0 (`tx.rollback` uses `syncOpenEditorBuffersForPath` so split's rollback
survives an open editor). Unit tests use the real bridge (`App.createConfigured__()` + real
`ResourceLockComponent`/`VaultTransaction`), 100% coverage.

The former integration-only branches are now fully unit-covered against `obsidian-test-mocks` ≥ 3.5.1,
so their `/* v8 ignore */`s are gone: the nested / differently-named folder-swap paths in `swapper.ts`
(3.5.0 made folder rename cascade to descendants and `getAvailablePath` de-duplicate), and the
backlink-rewrite `linkConverter` in `merge-composer.ts` (`fixBacklinks`) — 3.5.0 gave synchronous link
indexing and 3.5.1 fixed the markdown parser's link end offset to the exclusive `start + length`, so
dev-utils' `editLinks` write path now completes against the mock.

**Attachment-path unit tests need no local scaffolding** since `obsidian-test-mocks` ≥ 3.8.0 models the
resolution surface (`Vault.getConfig`/`setConfig`, `getAvailablePath`, `getAvailablePathForAttachments`,
`TFolder.getParentPrefix`), which retired the former `attachment-path.test-helpers.ts` seed. A suite just
calls `app.vault.setConfig('attachmentFolderPath', …)`; the vault root (`/`) is already the modeled
default, matching Obsidian. Two things the mocks deliberately do not give you:

- **Link settings have no modeled default**, and ODU's `getNewLinkFormat` feeds a `switch` ending in
  `assertNever`, so an undefined `newLinkFormat` THROWS once a merge rewrites a link. Set
  `newLinkFormat: 'absolute'` (deterministic — `shortest` would depend on the rest of the fixture vault)
  and `useMarkdownLinks: false`. Only `merge-composer.test.ts` reaches that path today; the other
  attachment suites do not, so they do not set them.
- **The attachment-location-plugin override** (Custom Attachment Location) is a third-party member, not
  Obsidian's: ODU dispatches to `app.vault.getAvailablePathForAttachments.extended` when present and
  ignores the native resolution entirely. `merge-composer.test.ts`'s `stubAttachmentLocationPlugin`
  installs one — `Object.assign(vi.fn(), { extended })` on the vault INSTANCE (the bridged member lives on
  `Vault.prototype`, so patching it there would leak between tests) — and that is how issue #161's claim
  that the destination comes from whatever patched Obsidian's resolution is pinned.
