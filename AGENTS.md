# AGENTS.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Advanced Note Composer is an Obsidian plugin that enhances the built-in Note Composer core plugin, adding richer merge, split, extract, and swap operations for notes (with frontmatter merge strategies, footnote/backlink fixing, heading-aware merging, and templating). It is built on `obsidian-dev-utils`.

## Architecture

- **Root config files** are thin re-exports — actual logic lives in `scripts/` (`eslint.config.mts` → `scripts/eslint-config.ts`, etc.).
- **`src/`** — plugin source:
  - `main.ts` — Obsidian entry point (default export of `Plugin`); imports the global SCSS.
  - `plugin.ts` — `Plugin` class (extends `obsidian-dev-utils` `PluginBase`); `onloadImpl` wires up settings, settings tab, all command handlers, the tokenized-string language component, and release notes.
  - `plugin-settings.ts` — `PluginSettings` class plus the `Action`, `EmptyFolderBehaviorAfterMergingFolder`, `FlattenMode`, `FrontmatterMergeStrategy`, `FrontmatterTitleMode`, and `TextAfterExtractionMode` enums; wraps `PathSettings` for include/exclude path filtering. **`FlattenMode` (issues #170/#171) collapses the two axes a flatten could have — WHAT moves and HOW DEEP it looks — into ONE enum** (`AllChildren` / `ChildFoldersOnly` / `AllFoldersRecursively`) rather than a scope enum plus a `shouldFlattenRecursively` toggle: the only combination anyone asked for is folders-at-any-depth, and the fourth cell of that cross product (dissolving every descendant FILE into the parent too) is a different operation nobody requested. **It is NOT a setting** — issue #177 turned it into the COMMAND IDENTITY: `plugin.ts` registers one `FlattenFolderCommandHandler` per member (`FLATTEN_MODES`), so the variant is chosen at INVOCATION time from the folder menu, and the settings tab has no flatten-mode row. `AllChildren` reproduces the pre-#170 behavior exactly and keeps the ORIGINAL `flatten-folder` command id, because a hotkey is bound to an id and hotkeys cannot be migrated by a settings converter; the two other ids start unbound. A leftover `flattenMode` key in an existing `data.json` is simply ignored, which is why neither #170 nor #177 needed a `registerLegacySettingsConverter`. `flatten-folder-command-handler.ts` translates the mode through the `FLATTEN_COMMAND_DEFINITIONS` and `FLATTEN_CONFIRM_SUMMARIES` `Record`s (keyed by the enum, so a new member is a compile error rather than a command left unregistered or a dialog left without wording) and hands it to `flatten-items.ts`. **`EmptyFolderBehaviorAfterMergingFolder` is a deliberate plugin-local WRAPPER around ODU's `EmptyFolderBehavior`, not that enum re-exported — do not "simplify" it back.** Issue #167 asked for a fourth option (keep the merged folder, delete the folders under it), and that is a change to WHICH paths are handed to `cleanupEmptyFolders`, not a new per-path behavior, so it is not expressible as an ODU value (G52/G61: nothing to extract upstream). Its three original members reuse ODU's exact string values (`'Delete'`/`'DeleteWithEmptyParents'`/`'Keep'`), which is what makes the retype need **no** `registerLegacySettingsConverter` — every already-persisted `data.json` value is still a valid member. `merge-folder-into-file-command-handler.ts` translates it through the `ODU_EMPTY_FOLDER_BEHAVIORS` `Record` (a `Record` keyed by the enum, so a new member is a compile error rather than an unreachable `switch` default the 100 %-coverage gate must reach) and, for `DeleteSubFoldersOnly` only, filters `folder.path` out of `folderPathsToCleanUp`. That member maps to plain `Delete` and never `DeleteWithEmptyParents`: with the merged folder kept, no ancestor of it can end up empty, so the parent half would be meaningless. **The two entry forms match differently** (ODU `path-settings.ts` `makeRegExp`): a plain path string compiles to `^<escaped>(/|$)`, so it covers the path **and its whole subtree**, while a `/regular expression/` is used verbatim against the raw path — which is the only way to express "the folder itself, not its contents" (`/^Inbox$/`). Issue #159 was that confusion, so both setting descriptions, the README `Include/exclude paths` section, and `demo-vault/21 …` spell it out, and `plugin-settings.test.ts` pins both forms. **Issue #155 (issue #159's other half — the reporter's own regex never persisting) is fixed**: a partially typed `/regular expression/` used to throw from ODU's `makeRegExp` on EVERY keystroke (`addMultipleText` → `bind` → `setProperty` assigns into `inputValues` *before* validating), popping an unhandled-error notice and aborting the debounced save. Since `obsidian-dev-utils` 88.4.0 `makeRegExp` returns `null` instead of throwing and the `PathSetting.array` setter absorbs it, so **one invalid entry makes the WHOLE list fall back to its default pattern** (`NEVER_MATCH` for Exclude, `ALWAYS_MATCH` for Include — both make `isPathIgnored()` return `false`, so a transient invalid value never hides anything). That fallback is silent by construction, which is why `plugin-settings-component.ts` registers ODU's exported `pathsValidator` on `includePaths`/`excludePaths` (imported, NOT hand-rolled — it was promoted out of Custom Attachment Location for exactly this second consumer) and `appendPathFormsDesc` states the all-or-nothing rule in both descriptions. Confirmed against real Obsidian by `exclude-paths-typing.desktop.integration.test.ts`, which types the reported value character by character and asserts no notice, that the completed value still reaches `data.json` (the save path was the second failure surface), and that an incomplete entry surfaces `Invalid regular expression: …`.
  - **`PluginSettings` holds TWO independent `PathSettings` instances (issue #198), and that split is load-bearing.** `_pathSettings` (`includePaths`/`excludePaths`, surfaced by `isPathIgnored`) is the CONTENT filter: what is off-limits as a picker entry, a merge/split target or source, and what a folder merge / flatten refuses to MOVE. `_commandPathSettings` (`commandIncludePaths`/`commandExcludePaths`, surfaced by `shouldBlockCommandOnPath`) is the COMMAND-VISIBILITY filter: whether the commands are offered at all. They were one list plus a `shouldBlockCommandsOnExcludedPaths` toggle until #198 — the client wanted commands hidden in a subtree that is still a valid merge destination, which one list could not express. **The toggle is REMOVED and must not be reintroduced**: two empty lists already make `isPathIgnored()` `false` (ODU defaults `ALWAYS_MATCH`/`NEVER_MATCH`), which IS the old toggle-off default, so a master switch would only add the incoherent "off, yet paths listed" state. `shouldBlockCommandOnPath` KEEPS its name and signature, which is why `command-block.ts` and the ~20 command-handler test stubs that fake it needed no change. Migration is a `registerLegacySettingsConverter` on `shouldBlockCommandsOnExcludedPaths` that seeds **both** halves from the old lists — the include half matters because the old blocking fired on `isPathIgnored`, which already accounted for `includePaths`, so copying only the exclude half would silently un-block everything outside a configured include list. Note the converter runs on the RAW `data.json` record, not a `PluginSettings` instance, so it reads plain properties rather than the class accessors; ODU then deletes the dead toggle key for free (it is in `LegacySettings` and no longer in `PluginSettings`). All four keys register ODU's `pathsValidator` — the silent all-or-nothing fallback of issue #155 is not specific to the content filter.
  - `plugin-settings-component.ts` — `PluginSettingsComponent` (settings load/save, value validators, legacy-settings converters).
  - `plugin-settings-tab.ts` — `PluginSettingsTab` settings UI (built with `SettingEx`/`SettingGroupEx`).
  - `tokenized-string-language-component.ts` — extends `obsidian-dev-utils` `SyntaxHighlightingComponent` and registers, through `registerPrismLanguageAsync`, the Prism language highlighting `{{token:format}}` template tokens. The language is not a code fence — only the settings tab's `CodeHighlighterComponent` fields render it — so only the Prism half of that component is used.
  - `release-notes-component.ts` — shows version release notes once on layout ready.
  - `swapper.ts` — `swap` logic for exchanging two files or two folders (with optional full folder-structure swap).
  - `headings.ts` — helpers to extract a heading from editor selection/line.
  - `heading-split-recursion.ts` — the two pure helpers behind the recursive split (issue #79 variant c / issue #156). `findNextHeadingToSplit(headings, minLevel)` returns the first heading at the *shallowest* level ≥ `minLevel`, so a note whose levels are skipped (`#` straight to `###`) or out of order still nests faithfully, and each extraction removes that heading's whole subtree so the next call returns the next sibling. `minLevel` is what stops the recursion eating itself: an extracted note still begins with the heading it was named after, so recursing into it with `minLevel` at 1 would extract its entire content into a nested copy of itself forever — callers pass the parent heading's level plus one, which also bounds the depth at `MAX_HEADING_LEVEL` (6). `buildRecursiveSplitPreviewRows(content, headings)` builds the confirmation dialog's list of notes-to-be-created by reusing `heading-sections.ts`'s tree (G52), so a skipped level is previewed at the depth it will actually nest at rather than at its heading level.
  - `horizontal-rules.ts` — `getSelectionBetweenHorizontalRules`, the range finder backing the `Extract between horizontal rules` command. It reads `metadataCache.getFileCache(file).sections`, filters `type === 'thematicBreak'` (which natively covers `---`/`***`/`___` and their spaced/longer variants, and excludes frontmatter delimiters + `---` inside code fences), and returns the `{ start, end }` `EditorPosition` range of the content between the rules nearest the cursor (document edges act as implicit boundaries; the bounding rules are excluded; leading/trailing blank lines are trimmed). Returns `null` when the note has no rules or the resolved section is blank — analogue of `getSelectionUnderHeading`.
  - `markdown-heading-document.ts` — parses markdown into a heading tree and merges documents heading-by-heading.
  - `insert-mode.ts` — `InsertMode` enum (append/prepend).
  - `move-selection-buffer.ts` — `MoveSelectionBuffer`, the transient holder for the "mark selection to move" feature (source note + captured selection + held source-note lock + the permanent notice); shared by the mark/move/cancel command handlers. `isOffsetInsideMarkedSelection` / `isRangeOverlappingMarkedSelection` reject an insert point/range that overlaps the marked text (a point is a zero-length range).
  - `mark-selection-to-move.ts` — `markSelectionToMove()`, the shared helper that locks the source note (blocking mutations), shows the marked-selection notice, and records the mark. The lock is taken with the dev-utils `lockForPath` `shouldReleaseOnAbort: true` + an `onUnlockRequested` callback that clears the buffer (identity-guarded on the mark's unique `abortController` so a stale controller can't cancel a later mark), so `Unlock active note` — which aborts every lock on the note, cancelling all operations that hold one — also releases the lock and tears the mark down (buffer cleared, notice hidden, highlight removed) without any hand-wired `abort` listener. Takes `shouldLockAllNotes`: when off it locks only the source note (`mode: 'file'`); when on it subtree-locks the vault root (`app.vault.getRoot().path`, `mode: 'subtree'`) so every note is read-only until the move completes or is cancelled. Used by the `Mark selection to move` command (passing the `shouldLockAllNotesWhenMarkingSelection` setting) and the split picker's "switch to smart cut".
  - `selection-highlight-component.ts` — `SelectionHighlightComponent`, persistently highlights the captured selection of a pending operation (a smart-cut mark, or a split/extract while its picker is open) in its source note. A CodeMirror 6 `StateField` (`selectionHighlightField`) + `setSelectionHighlightsEffect` (registered once via `plugin.registerEditorExtension`) renders the decorations; `addHighlight(file, ranges)` returns a `Disposable`, and `refresh()` (on add/remove + `active-leaf-change`) dispatches the effect to every markdown editor. The `@codemirror/*` imports are externalized by the dev-utils build, so they use Obsidian's runtime CM instance. Pure range logic (`computeHighlightRangesForFile`, `mergeHighlightRanges`, `buildSelectionHighlightDecorations`) is unit-tested; the workspace/editor glue (`refreshLeaf`) is `v8 ignore`d and confirmed via a desktop integration test.
  - `move-notice-component.ts` — `MoveNoticeComponent`, owns the permanent "Smart cut & paste" notice while a selection is marked. Builds it with up to four `ButtonComponent`s — move to top / bottom / at cursor (each `MoveMarkedSelectionEditorCommandHandlerBase.executeInActiveEditor()`), and Cancel move (`CancelMoveCommandHandler.cancelMove()`). Enabled state is refreshed via each move handler's `canExecuteInActiveEditor()` on `active-leaf-change` + `selectionchange`; the Cancel button is always enabled. The notice is non-dismissable — shown with `shouldHideOnClick: false` and `shouldShowCloseButton: false` (no `X`), so the only way to release the mark is the Cancel move button (or a programmatic `MoveSelectionBuffer.clear()`, which hides the notice); there is no `onHide`/close-confirmation auto-cancel (removed in issue-140, where clicking any button or the `X` was dismissing the notice before the action ran). **Configurable via the `Smart cut & paste` settings** (read from the injected `pluginSettingsComponent` at `showNotice()` time): each of the three move buttons is included only when its `shouldShowMove{ToTop,ToBottom,AtCursor}Button` flag is on (Cancel always shown), and when `shouldShowSmartCutNotice` is off `showNotice()` shows nothing and returns `null` (so `MoveSelectionBuffer` / `MarkedSelection.notice` are `Notice | null`, and `clear()` guards `notice?.hide()`). Defaults are all `true`, preserving the prior always-four-buttons behavior. The notice also carries an always-shown **`Swap with selection`** button (before Cancel move) backed by `SwapMarkedSelectionEditorCommandHandler` (an `ActiveEditorCommandHandlerBase` subclass that is NOT registered as a command, so it has no hotkey / no main-editor key interception — issue #148): it swaps the smart-cut-marked selection with the active editor's current selection via the shared `swap-selection-runner.ts` (`canSwapWithSelection` / `swapWithSelection`, extracted from `SwapWithMarkedSelectionEditorCommandHandler` so both the swap command and the notice button share one code path — G52). The button is enabled only when the mark covers a single selection and `canExecuteInActiveEditor()` passes (source still exists, active editor has a selection, non-overlapping for a same-note swap); on click it clears the mark (releasing the pending source lock, mirroring the move handoff) and runs the swap in a reversible resource-locked transaction that locks both notes. Covered by `move-notice-component.test.ts` + the real-Obsidian `smart-cut-notice-settings.desktop.integration.test.ts` + `swap-marked-selection.desktop.integration.test.ts`.
  - `operation-notices.ts` — the ONE place that knows what an operation notice looks like and whether it is shown (issue #182). `buildOperationNoticeContent` renders `<verb> <source>[ <preposition> <target>][suffix]` closed either by the `is-loading` spinner (a progress notice) or a period (a completion notice); `showOperationProgressNotice` (delayed, 500 ms, so a fast operation never flashes), `showOperationPermanentProgressNotice` (the two batch merges, which are long by construction) and `showOperationCompletionNotice` all gate on the new `shouldShowOperationNotices` setting. **The completion notice is STANDALONE (`isReusable: false`), and that is a bug fix, not a preference:** a reusable notice takes the single per-plugin slot and silently replaces whatever is in it, so the first version of this erased the folder merge's "N file(s) were not merged because they are ignored" summary (caught by `merge-folder-skips-ignored.desktop.integration.test.ts`, which timed out waiting for it). An operation can have more than one thing to say, and the two summaries are emitted on either side of the completion notice depending on the flow, so neither may own the slot. **The audit that produced this is the finding worth keeping: the plugin was never silent, it was INCONSISTENT** — four different mechanisms (permanent `is-loading` notice, delayed progress notice, `shouldShowSmartCutNotice`'s interactive notice, `smartCutAndPasteCompletionFeedback`) applied unevenly, and nothing except the recursive split and the selection swap ever said "done". `ComposerBase.buildProgressContent` now delegates here and gained a `buildCompletionContent` sibling (G52 — one shape, not two). **`shouldShowSmartCutNotice` was deliberately NOT reused as the gate**: it gates an *interactive* notice, so turning it off removes buttons rather than information; and `smartCutAndPasteCompletionFeedback` is left alone because it already owns how a finished move announces itself — which is why `SplitComposer` skips its completion notice when `smartCutAndPasteMoveKind` is set (and when `isMultipleSplit`, where the command handler reports once for the batch). **`shouldLinkSource: false` is not cosmetic**: an operation that CONSUMES its source (a merge trashes the note, a folder merge trashes the folder, a move renames it away) must render that path as plain text, because an internal link to a path that no longer exists renders unresolved and **clicking an unresolved note link CREATES that note** — the notice reporting a deletion would otherwise offer to undo it by accident. For the same reason the swap/move handlers capture `path` into a `const` BEFORE the transaction: a rename mutates `TAbstractFile.path`, so reading it afterwards reports the two sides the other way round. The setting defaults to `true` and needs **no** `registerLegacySettingsConverter`, but unlike the plugin's other migration-free settings that default deliberately CHANGES behavior for an existing vault — reporting every operation IS the feature — so do not "fix" it later by flipping the default. Refusal/error notices are never gated. Confirmed against real Obsidian by `operation-notices.desktop.integration.test.ts` (a real `Flatten folder...` reports `Flattened folder … into …, promoting N item(s).` in `activeDocument`, and reports nothing with the setting off; it matches the notice by the run's OWN folder name because the previous run's notice lingers for its full duration).
  - `recent-suggestions.ts` — the ONE place that knows "recently-opened, most-recent-first", shared by every picker (renamed from `recent-folder-suggestions.ts` when it grew the file half). `getRecentPaths` (renamed from `getRecentFilePaths` in issue #206, since it now also yields FOLDER paths) wraps `workspace.getRecentFiles` with a single reconciled option set and an explicit `maxCount: 50` (Obsidian's own default is **10**, which silently truncated the recent list); `reorderSuggestionsByRecentFolders` / `reorderSuggestionsByRecentFiles` front-load the resolved folders/files, filtered by the caller's own constraint and de-duplicated, ahead of the fuzzy suggestions (empty query only). Consumers: the merge/move/swap **folder** pickers, the swap **file** picker, and `SuggestModalBase.getRecentFiles()` (which no longer passes its per-type flags — `shouldIncludeFile` applies the same ones). **Issue #158 — why the folder pickers pass `shouldIncludeActiveFile: true`:** Obsidian's `RecentFileTracker` collects the file you just **LEFT**, not the one you just opened (`Workspace`'s active-leaf change calls `recentFileTracker.onFileOpen(newFile, previousFile)` and the tracker collects the SECOND argument), so the note you are on is never at the head of `getRecentFiles()` — visiting A→B→C leaves `[B, A, …]` with C active. A folder picker asked for "the folder I am on" therefore has to prepend the active file itself; de-duplication keeps that prepended copy first even when the active file also sits further down the list. File pickers pass `false`: their source IS the active file and they already exclude it. Confirmed against real Obsidian by `recent-folder-order.desktop.integration.test.ts` on BOTH ends (G99: catalyst 1.13.4 + public 1.12.7), which also asserts the Obsidian-internal premise so a change upstream fails loudly. Note the ordering assertion in `move-folder.desktop.integration.test.ts` is deliberately hard-coded — deriving it from `getRecentFiles()` the way the production code does made it pass under any ordering, which is why #158 shipped.
  - `recent-targets.ts` — the plugin's OWN recency, and the other half of what a picker orders by (issue #206). Obsidian tracks only which files were OPENED, so a folder that served as a `target` / `destination` left no trace at all and had to be clicked into the ranking before the next operation could offer it — which is exactly what the reporter asked not to have to do. `recordRecentTarget` / `getRecentTargetPaths` / `clearRecentTargets` keep one move-to-front, 50-deep list of **paths**, files and folders together, and `getRecentPaths` puts it in FRONT of everything, the active file included. **That precedence is the owner's call, and it is the one place #206 and #158 disagree:** the ask is that a destination used once is "always the top one on the list" for the operations that follow, and the two rules only ever collide when the user runs a second operation without first navigating into the folder the previous one landed in — the case the request is about. **One list, three readers, no per-kind bookkeeping:** the folder resolver became `getFolderByPath(path) ?? getFileByPath(path)?.parent`, which makes a recorded folder resolve AND makes "the folder a note was merged into counts" fall out of the same lookup; the file readers keep `getFileByPath`, so a recorded folder resolves to nothing there and is silently skipped. **Recorded on COMPLETION, never on selection or confirmation** — a cancelled or rolled-back operation must not teach the ranking anything — so the calls sit beside each flow's completion notice rather than inside `showOperationCompletionNotice`, which is gated by `shouldShowOperationNotices` and skipped by some flows. `ComposerBase.recordTargetFileAsRecent` covers every single-note merge/split/extract, guarded on `injectedVaultTransaction`: a composer inside a batch's transaction records nothing (that transaction can still roll back), and the batch's own runner records once instead. **`SplitComposer` additionally skips a batch split (`isMultipleSplit`) because there is no target the user CHOSE** — `prepareForSplitFile` resolves each produced note's location from the settings with no picker — and recording every note of a recursive run would bury the list under one operation's output; the recursive split records the root folder the user picked, once, itself. A swap and a move pass the captured PATH rather than the object, since both RENAME their target and `TAbstractFile.path` would by then report the other side. **Session-only, in memory: no setting, no `data.json` key, no `registerLegacySettingsConverter`** — `plugin.ts` drops the list on unload, so a reload starts from Obsidian's own recency. Confirmed against real Obsidian by `recent-target-order.desktop.integration.test.ts` (a folder nobody opened a note in leads the picker after a real move lands in it, ahead of the folder of the note the user is on). Consequence for the ordering tests that came before it: the absolute "first suggestion is X" assertions in `recent-folder-order.desktop.integration.test.ts` and `move-folder.desktop.integration.test.ts` became RELATIVE, because a suite earlier in the aggregate run can legitimately record a target that outranks them — the reported bugs were about relative order anyway.
  - `filename-validation.ts` — regexes for invalid filename characters / trailing dots-or-spaces, plus the shared `fixFileName` that turns typed text into a valid file name (invalid characters and leading/trailing dots-or-spaces replaced per `shouldReplaceInvalidTitleCharacters`/`replacement`; `/` folded into a collapsed single segment when the name is not treated as a path). Extracted out of `SplitItemSelector` once the folder-merge target name (issue #160) needed the same rules; `SplitItemSelector.fixFileName` is now a thin delegate. **Still SYNCHRONOUS and pure on purpose** — issue #196's transform is a separate step in front of it (`name-transform.ts`), not a parameter of it.
  - `name-transform.ts` — the `nameTransformTemplate` setting (issue #196): the vault's OWN replacements, instead of living with one universal `replacement` character. `applyNameTransform` resolves the plugin's `{{rawString}}` (plus the shared `{{date}}`/`{{time}}`) and, only if what comes out still holds a `<%`, hands it to Templater with the same `TOKENS` binding `templater-prelude.ts` gives created notes — so `<% TOKENS.rawString.replaceAll(": ", " - ") %>` is a mapping and a conditional one is just as easy. `transformAndFixFileName` is the transform-then-`fixFileName` pair, and it exists so the call sites cannot disagree about the ORDER: transforming first is what makes the feature work at all, since the other way round `:` would already be `_` and the template would have nothing to map. **A TEMPLATE rather than a `FROM => TO` list** because a list can only express the substitutions someone already thought of — which is also why Templater is required for anything conditional; a second mini-language that could branch would just be a worse Templater. **Every failure THROWS a `NameTransformError` — nothing is silently left untransformed** (the user configured a rewrite precisely so a name would not be mangled behind their back): the `Create folder with notes...` prompt validator catches it and re-asks with the typed text intact — which is why `prompt`'s `valueValidator` being `Promisable` matters — and the other flows abort before creating anything. **The failures are TYPED, and the type is the whole point (issue #203):** those other flows now report the message themselves — `split-file-modal.ts`'s `selectSplitTarget` and `merge-folder-into-file-command-handler.ts`'s `resolveTargetPaths` catch exactly `NameTransformError`, show it via `pluginNoticeComponent` and cancel — and a caller that caught `Error` instead would turn every genuine bug in the selector into a polite notice. Before that, a misconfigured template surfaced as ODU's generic `An unhandled error occurred. Please check the console for more information.`, which named neither the setting nor the problem, and the two `Create folder with notes...` validators are the only places the catch can be exhaustive (nothing else there throws), which is why their defensive rethrow is `v8 ignore`d rather than tested. **A transformed name must be a SINGLE LINE** (`ensureSingleLineName`, checked after the `.trim()` on both exits, so a `-%>` block's trailing newline is still fine). That IS issue #203: the reporter wrote one Templater command per LINE (`<% … replaceAll(": ", " - ") %>\n<% … replaceAll("?", "_") %>`), each command emits its own result, so `Test: a` became `Test - a\nTest: a` — and a line break is not an "invalid character" `fixFileName` can replace (it is not in `INVALID_CHARACTERS_REG_EXP`, and no file system accepts one), so it survived every sanitization step and only failed at `vault.create`. With `shouldSplitHeadingsAutomatically` on — their setting — `Extract this heading...` skips both the picker and the confirmation, so the name was never shown to anyone before it was used; the recursive split failed identically, once per heading. It is REFUSED rather than joined: joining would have silently produced `Test - a Test  a` and traded a loud failure for a wrong name, which is what the "every failure throws" rule exists to prevent. **`contextFile` is not optional decoration**: Templater reads `target_file.basename`/`.stat` EAGERLY while generating its function object, so a run with no file dies with `Cannot read properties of undefined (reading 'path')` (verified against Templater 2.25.0, which also confirmed `parse_template(config, content)` + `create_running_config(undefined, targetFile, RunMode.DynamicProcessor = 4)`); the split passes its SOURCE note, everyone else falls back to the active note and refuses with a message that says so when there is none. **The transform runs ONCE, where a name enters from outside** — `create-folder-with-notes-command-handler.ts` `normalizeNoteName` and `SplitItemSelector.resolveNoteBasenameInOwnFolder` deliberately SKIP it, because their input is built from tokens that already carry the transformed name and running it again applies the rewrite twice (`{{rawString}} notes` over `alpha` produced `Alpha Notes notes` — caught by a test, not by review). What the transform leaves invalid is NOT its problem: `shouldReplaceInvalidTitleCharacters` decides, and turning it OFF is issue #196's "block the characters that have no replacement" — the existing refusal paths already do it, which is why the request needed no setting of its own. Empty template = the transform is skipped entirely = pre-#196 behavior, so no `registerLegacySettingsConverter`.
  - **`Create folder with notes...` (issue #191) — `create-folder-name.ts`, `next-folder-index.ts`, `folder-content-template.ts`, `templater-prelude.ts` and `command-handlers/create-folder-with-notes-command-handler.ts`.** Creates a folder plus the notes inside it from a prompt. **The spec is not the issue text — it is the reporter's OWN plugin**, `folder-note-extended`, which shipped inside the issue's `Tester 1.zip` sample vault and answers every question the issue leaves open (the `N.` prefix, `next = 1 + max` over siblings matching `/^(\d+)\./`, the Title-Case-except-acronyms rule, the note being opened afterwards); the attached video shows it end to end. What differs here is that each of their hard-coded decisions became a template, which is what lets one command serve their layout and everyone else's without a setting per decision. **`create-folder-name.ts`** applies their `sanitizeFolderName` order verbatim — trim, strip leading/trailing dots, collapse whitespace, Title Case (a word that is entirely upper-case and longer than one character is left alone), then the shared `fixFileName`. The dots are STRIPPED rather than left to `fixFileName`, which would replace them with `replacement` (`.Notes.` should be `Notes`, not `_Notes_`), and no second invalid-character setting exists — `shouldReplaceInvalidTitleCharacters`/`replacement` already are it. **`next-folder-index.ts`** derives the "already numbered" pattern FROM the name template: `{{index}}` becomes `(\d+)` and **every other token becomes `.*`**. That second half is load-bearing — substituting the real values would produce a pattern matching only a folder of the same name, so the scan would find nothing and every folder would be numbered `1`. That second case probes all five in ONE closure with a per-modal `try`/`catch` — a throwing `waitUntil` would discard everything the earlier probes had already observed — and returns the failures so they are reported from outside Obsidian. `open-minimizable-modal.test.ts` pins the opener itself, which is the cheap guard that fails the moment anyone re-points a confirmation dialog at `openModal`. **Since `obsidian-dev-utils` ≥ 92.0.0 the wrapper changes a SECOND thing, and the two openers now differ in two ways rather than one (issue #202): clicking the dimmed background of a wrapped modal MINIMIZES it instead of cancelling the operation it is running.** The reporter's complaint was that a stray click past a confirmation menu threw away the whole pending command; a click is not a deliberate cancel, so it now parks the dialog on the floating bar and the operation stays alive. `MinimizableModalConstructorOptions.shouldMinimizeOnClickOutside` defaults to `true`, so — exactly as with `shouldShowCancelButton` — the wrapper passes **no** option and every minimizable modal gets it. Do NOT "restore" the native behavior thinking it was lost by accident. What still cancels is unchanged and deliberate: `Escape` (`ConfirmDialogModal`'s own `scope.register([], 'Escape')`), the dialog's Cancel button, and the bar's ✕ — a keypress or a button press is deliberate in a way a background click is not. **The plain `openModal` pickers keep dismissing on a background click**, since they are never wrapped: minimizing them was ruled out by #125, and there is no half-finished operation to protect before a target has been chosen. Upstream in dev-utils it is a capture-phase `click` listener on `containerEl` that `preventDefault()`s and `stopImmediatePropagation()`s — Obsidian registers its own dismissal on `bgEl` inside the `Modal` constructor and calls `close()` directly there, so nothing overridable and no prevented default can stop it from a listener on the same element. Confirmed against real Obsidian by `modal-background-click-minimizes.desktop.integration.test.ts`, which pins all three sides: the flatten confirmation parks and still completes after a restore, `Escape` still cancels it, and the initial merge picker is still dismissed by the same click.

## Resource locking & transactional rollback

Every merge/split/swap operation (files **and** folders) locks the resources it touches
(`ResourceLockComponent.lockForPath({ shouldBlockMutations: true })`) against edit/delete/rename/move,
detects external changes and aborts, and runs its vault mutations inside a reversible dev-utils
`VaultTransaction` that commits on success and rolls back on cancel/error. The shared runner is
`src/locked-transaction.ts` (`runLockedTransaction`), used by the composers and the swap/merge-folder
handlers; folder-merge threads one spanning transaction into each `MergeComposer`. Requires
`obsidian-dev-utils` ≥ 84.1.0 (`tx.rollback` uses `syncOpenEditorBuffersForPath` so split's rollback
survives an open editor). Unit tests use the real bridge (`App.createConfigured__()` + real
`ResourceLockComponent`/`VaultTransaction`), 100% coverage.

The former integration-only branches are now fully unit-covered against `obsidian-test-mocks` ≥ 3.5.1,
so their `/* v8 ignore */`s are gone: the nested / differently-named folder-swap paths in `swapper.ts`
(3.5.0 made folder rename cascade to descendants and `getAvailablePath` de-duplicate), and the
backlink-rewrite `linkConverter` in `merge-composer.ts` (`fixBacklinks`) — 3.5.0 gave synchronous link
indexing and 3.5.1 fixed the markdown parser's link end offset to the exclusive `start + length`, so
dev-utils' `editLinks` write path now completes against the mock.

**Attachment-path unit tests need no local scaffolding** since `obsidian-test-mocks` ≥ 3.8.0 models the
resolution surface (`Vault.getConfig`/`setConfig`, `getAvailablePath`, `getAvailablePathForAttachments`,
`TFolder.getParentPrefix`), which retired the former `attachment-path.test-helpers.ts` seed. A suite just
calls `app.vault.setConfig('attachmentFolderPath', …)`; the vault root (`/`) is already the modeled
default, matching Obsidian. Two things the mocks deliberately do not give you:

- **Link settings have no modeled default**, and ODU's `getNewLinkFormat` feeds a `switch` ending in
  `assertNever`, so an undefined `newLinkFormat` THROWS once a merge rewrites a link. Set
  `newLinkFormat: 'absolute'` (deterministic — `shortest` would depend on the rest of the fixture vault)
  and `useMarkdownLinks: false`. Only `merge-composer.test.ts` reaches that path today; the other
  attachment suites do not, so they do not set them.
- **The attachment-location-plugin override** (Custom Attachment Location) is a third-party member, not
  Obsidian's: ODU dispatches to `app.vault.getAvailablePathForAttachments.extended` when present and
  ignores the native resolution entirely. `merge-composer.test.ts`'s `stubAttachmentLocationPlugin`
  installs one — `Object.assign(vi.fn(), { extended })` on the vault INSTANCE (the bridged member lives on
  `Vault.prototype`, so patching it there would leak between tests) — and that is how issue #161's claim
  that the destination comes from whatever patched Obsidian's resolution is pinned.
